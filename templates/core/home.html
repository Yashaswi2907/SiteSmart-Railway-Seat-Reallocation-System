The reallocation engine

A seat isn't simply taken or free.
It's taken between stations.

Each route is split into segments — the stretch between consecutive stations. A booking occupies only the segments it travels, so one berth can carry several passengers on the same run as long as their journeys never overlap.

  1. 01
    TT verifies a no-show
    Once the train reaches the boarding station, the TT marks the passenger as Did not board.
  2. 02
    Remaining segments are released
    Segments still ahead of the train become bookable. Segments already travelled stay closed for good.
  3. 03
    Upcoming passengers book the gap
    Best-fit selection fills released gaps first; overlapping requests are rejected by the engine and by a database constraint.

Engineering

Correctness first

The allocation engine is a set of small, tested Django services. Availability is revalidated inside a locked transaction right before every booking is written.

Per-segment occupancy

One allocation row per seat, run date and segment — the same model the TT console and analytics read.

No double booking, ever

Immediate-mode SQLite transactions plus a partial unique index make overlapping allocations impossible.

Position-aware

Once the simulated train leaves a station, segments behind it can never be sold again.

Verifiable tickets

PDF e-tickets carry a signed QR code that the verification page checks for tampering.
